# note記事に向けた原文・編集履歴

2026-09-12。今回はデータ構造と収集まで。記事の自動生成、noteへの公開、人格の自動更新は行わない。

## 保存するもの

| シート | 1行の単位 | 用途 |
| --- | --- | --- |
| SourceRevisions | 1回答または補足回答の、観測した1版 | 本人の一次資料。原文、質問、テーマ、回答日時、保存日時、Slackのchannel/thread、画像参照、訂正前の版ID |
| EditorialHistory | 1投稿の本文・状態の観測版 | AI草稿と本人による手直し・承認・却下を区別。前のイベントID、原文の版ID、編集理由、生成時の編集メタデータ |
| ArticleDrafts | 将来の1記事の1版 | 記事本文、前の版、文体プロファイル版、モデル・プロンプト版、確認事項、公開URLの保存先。現在は空 |
| ArticleSources | 記事の1節と原文の1版の対応 | 原文引用、利用方法、確認状況。現在は空 |

列定義の正は `gas/src/Sheets.js` の `SHEET_HEADERS`。Stockの末尾に `source_revision_ids` を追加する。既存の列や行を削除・並べ替えしない。

`source_id=interview:<session_id>:Q<idx>:answer|followup_answer` は回答の固定ID。`revision_id` と `event_id` はUUID。本文・質問・日時・画像参照のハッシュが変わると新しい行を追加し、前の版を上書きしない。元の文章へ戻したときも新しい版になる。回答セルの空欄化・スキップは `deleted=true` の版を残す。

`source_time` は回答が保存された日時であり、話題にしている出来事の日付とは限らない。`observed_at` は今回の版を収集した日時。これを混同して「当時の人格」や見解の変化を自動断定しない。原文中の留保・対立仮説・判断条件を残したまま、将来の執筆時に時系列を確認する。

## 収集経路

- 導入時と夜の品質ゲート開始前に、既存InterviewsとStockを一括回収。同じ状態は重複保存しない。
- インタビュー回答・補足の更新前後で回収。下書き生成前にも実際にモデルへ渡す回答の版を固定する。会議が失敗しても原文の履歴は残る。
- 新しい短文・分割・長文の下書きに、生成時に取得した原文の版IDを記録する。既存投稿には生成当時の原文IDを推測して付けない。
- 管理UIの本文編集、個別承認・却下、一括承認を `actor_type=user` として記録。モデル生成は `model`、後から観測した状態やSheets上の編集は `unknown`。承認はその投稿を採用した証拠であり、AIが書いた全文章を本人の原体験や信念に昇格させるものではない。
- `api_updateText` / `api_setStatus` の任意の第4引数 `reason` は将来のUI拡張用。現行UIでは理由入力は求めず、理由未入力は空欄のまま保存する。
- Sheetsの直接編集は専用onEditトリガーで該当行を回収。トリガー実行時に観測できた状態を保存する。スクリプト/APIの編集ではonEditが動かないため、保存箇所のフックと夜の回収を併用する。

原文はInterviewsが正。アーカイブに障害があっても回答の保存を妨げず、`article_archive_error` をLogへ記録する。次回回収で現在の内容を再取得する。保存失敗時は新投稿の出典IDを空配列とし、出典が確定したことにしない。

導入前に上書きされて失われた旧文、取得失敗中や連続編集の合間に消えた中間版、物理的に削除された行の完全復元はできない。これは観測版の保存であり、全操作の完全な監査ログではない。行削除の代わりに回答セルを空にすると削除版が残る。新しい収集表の本文・IDは直接編集せず、原文の訂正はInterviewsで行う。

## 将来の記事での利用条件

SourceRevisionsの `publication_scope` は、既定 `review_required`。当該版を記事に使ってよいと本人が確認した場合に `allowed`、非公開は `private` とし、必要なら `reason` に理由を残す。これらは将来の記事用途の区分であり、既存X投稿の審査・公開ルールは変えない。

原文が改訂されたら、公開可の判断を新しい版へ自動継承しない。新しい版は再び `review_required`。`private` は訂正後も継承する。`getArticleSourceBundle()` は最新かつ公開可の原文だけを返し、`getArticleSourceBundle(true)` は確認用に要確認原文も含める。いずれも非公開・削除・Interviewsに存在しない/本文が一致しなくなった版とAI投稿は除外する。

将来の執筆機能は、記事の節ごとに `ArticleSources.source_revision_id` を付け、引用を当該版に照合する。執筆時と公開前に最新原文・公開区分・本人の確認を再チェックする。過去に公開可だった版を参照して最新の非公開指定や訂正を回避しない。まず3人格の提案・異論・確定意見、ミアの編集判断、編集者による執筆、原文との照合と本人承認を通す。これらの執筆・公開処理は今回未実装。

## 導入と確認

1. Ubuntuで `cd ~/X_autopost && git pull origin main && cd gas && ./deploy.sh`。管理UIのAとSlackのBの両デプロイを更新する。
2. GASエディタで **ArticleArchive.gs**（`gas/src/ArticleArchive.js`）を開き、`setupArticleArchive` を1回実行する。4シートとStockの1列を追加し、現在のデータを一括保存、専用onEditトリガーを登録する。既存の定期トリガーは変えない。再実行しても同じ内容やトリガーは重複しない。
3. SourceRevisionsに原文と日時、EditorialHistoryに既存投稿が入ったことを確認する。ArticleDraftsとArticleSourcesが空なのは正常。この記事準備処理はSlack通知・AI呼び出し・X投稿をしない。
4. 途中で収集が失敗した場合は同じ **ArticleArchive.gs** の `captureArticleArchive` を実行する。これも手動回収だけ。

導入関数をまだ実行しておらず収集表が存在しない場合、アーカイブは休止し、通常のインタビュー・編集を続ける。`setupSpreadsheet` でも新表は作られるが、直接編集トリガーの登録と既存資料の取り込みには `setupArticleArchive` を使う。

Nodeの回帰テストは実APIなしで、取り込みの反復、訂正・補足・取り消し、削除・公開区分、モデルと本人操作の区別、生成失敗時の原文保持、出典版の固定、ロック所有権、収集失敗時の回答保存を検証する。GASでの権限・トリガー実行と本番データの保存はデプロイ後の確認が必要。
