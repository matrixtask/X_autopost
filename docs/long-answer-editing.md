# 長文回答の編集・ストック

長い回答を短文2案へ押し込むと、判断の背景や留保が落ちる。通常ポストの280重みを超える回答がセッションにある場合、編集者リナが各回答の掲載形式を選ぶ。文字数は編集経路へ入れる目安であり、分割か長文かの判断基準ではない。短い回答だけのセッションは既存の生成経路を維持する。

## 形式の選択

| 形式 | 選ぶ場合 | ストック・投稿 |
| --- | --- | --- |
| 独立した分割 | 異なる発見や判断があり、各々に必要な前提・意味・留保を置いて単独で読める | 1回答から2〜4本、各280重み以内。各々を承認・予約し、順不同・別の日でも成立 |
| 長文1本 | 背景→転換→理由→結論を一緒に読む価値があり、分割すると誤解や薄まりが生じる | 280重み超〜4000文字。全文をStockの1行に保存し、1枠で投稿 |
| 短文1本 | 冗長な説明を整理すると、一つの固有な発見を短く完結できる | 280重み以内、1枠 |

分割は代替案の言い換えや返信スレッドではなく、それぞれ公開できる独立稿。続きの投稿を読まないと誤解する構成は長文を選ぶ。採用理由、他形式で失われるもの、省いた材料も記録する。全体は最大8本・本文合計6000文字。4000文字はアプリの編集上限で、Xのサービス上限とは別。

長文の冒頭には本人回答にある具体的な判断・場面・違和感を置き、後半で理由や結末を回収する。冒頭だけでも逆の意味にならないよう必要な留保を先に置く。空行の水増し、文の機械切断、根拠のない煽り、出し惜しみは採らない。「さらに表示」の位置はX側の表示に依存し、指定・保証しない。

## 人格と工程

全員が架空の編集視点。実在の専門家による独立検証ではない。

1. レイ・セバスチャン・ハンニバルが提案、相互異論、確定意見を出す。分割の独立性と、一体で読む文脈の価値を比較する。
2. ミアが採否・方向性・原文の核を確定する。複数の発見を一つの一般論へ薄めない。
3. **リナ（rina）**が形式を選び、本文を編集する。架空の長文編集者として本人の声・論理・意外な発見を守り、読む順番を整える。別回答の事実を混ぜず、体験・数字・採用CTAを創作しない。
4. プログラムが出典、原文引用、ミアの核、形式・本数、文字数、完全重複を検証。全グループの検証後に一括保存する。JSON途中救出で後半を失わない。
5. 品質ゲートで本文全文・原文回答・同じグループの全稿を読む。通常の資料照合・公開範囲・5軸参考値に加え、3人格＋ミアで編集後の構成を審査する。
6. 通過は人の承認待ち。異論が残れば保留で本文引用・理由・編集指示を残す。審査の欠損や引用捏造は再評価待ちに留める。

編集後のレイは留保・因果・忠実さ、セバスチャンは初見の理解と仕事の実像、ハンニバルは独立性・重複・形式選択の代償、ミアは冒頭と結末の対応・意外さの保持を担当する。

生成は会議→ミア→リナの3APIで既定OpenAI。保存後の採点・構成審査は既定Claudeの1APIに統合し、新編集案は1件ずつ処理する。時間予算不足なら保存済み稿の審査を夜へ回す。旧モードでも新編集案はこのゲートへ送り、自動承認・短文専用リライトを適用しない。

## 保存と表示

- 新列: `post_format / edit_group / part_index / part_count / edit_reason / edit_meta / edit_review`。既存列・行を削除せず、生成時の `ensureHeaders` で追加。
- 元回答はInterviewsに保持。Stockは `session_id / source_idx` で対応し、分割稿は同じ `edit_group` を共有。モデルにテーマ・カテゴリ・画像を決め直させない。
- 管理画面は形式、元回答の番号・日付・テーマ、編集理由、全文を表示。長文は全文のまま編集できる。
- 新編集案の承認・予約後の本文変更は承認を解除し、予約時刻と旧評価を消して再審査する。
- Slackの長文はプレビューと明記し管理画面へ案内。複数稿とコメントは通知を分けて欠落を防ぐ。
- NotionのBodyはrich_textを複数要素に分け、従来の1900文字での切り捨てを廃止。
- 会議版 `council-v3`、編集版 `composition-v1`。過去の投稿・下書きは自動で書き換えない。

## 導入

2026-09-12にユーザーがアカウントの長文利用可能を確認。`X_LONG_POSTS_ENABLED` 既定true。falseなら長文の予約・送信だけを止め、全文は保存する。DRY_RUN・人の承認・予約枠は従来どおり。POST /2/tweetsへ全文を送り、APIが拒否した場合はfailedにして本文を保持する。短縮投稿へのフォールバックはない。

Ubuntuで実行し、A（管理画面）・B（Slack）の両デプロイを更新する。

```bash
cd ~/X_autopost
git pull origin main
cd gas
./deploy.sh
```

新しい内部関数は **PostComposition.gs**（`gas/src/PostComposition.js`）。`Pure.gs`に形式別の文字数・表示名、`Notion.gs`に全文分割、`Interview.gs`に通知分割も追加。手動実行不要。先に列を作る場合のみ **Sheets.gs** を開いて既存の `setupSpreadsheet` を実行できる。

## 検証と制約

`npm test` で生成順序・各形式の保存、一括保存、出典/引用/重複/本数/文字数、審査欠損と異論、審査中の変更、承認後の編集、全文表示/同期、通知分割、legacy保護、予約と送信、API拒否時の原文保持を検証する。

実モデルの編集品質・生成時間・採用やフォローへの効果、GAS本番・実際のX長文送信は未検証。折り畳み位置を検証済みとは扱わない。元回答が12000字を超えると既存の資料照合上限により保留になる。原文を切って照合済みにはしない。必要なAPIが時間予算を超えた場合も回答または保存済み稿を保持する。

参照: [Xの長文ポスト](https://help.x.com/en/using-x/x-premium-how-to)、[投稿API](https://docs.x.com/x-api/posts/create-post)、[Notion rich_textの上限](https://developers.notion.com/reference/request-limits)。
